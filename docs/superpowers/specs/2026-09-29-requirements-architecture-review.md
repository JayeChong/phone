## 评审结论

整体方向可行。ESP32-S3、LVGL 单渲染线程、独立系统服务、按需 Worker 和有限 APP 页面缓存的组合，适合当前硬件，也能支持桌面分页、最近任务、电话、相机、相册和设置等目标。

首次评审发现若干开工前高风险问题，其中最关键的是：蜂窝语音能力尚未通过目标 SIM 和网络验证、多个业务共用 A7670 UART 却没有唯一串口所有者、部分启动绑带脚缺少整机启动验证，以及远程位置和拍照功能缺少安全模型。设计缺口现已完成处置；硬件事实仍必须在阶段 0 通过真机验证。

本报告保留首次评审时的问题描述，用于解释风险来源。2026-09-29 已完成方案确认，最终决策已同步到 [手持终端需求文档](../../需求.md) 和 [桌面与 APP 架构设计](./2026-09-29-handheld-desktop-architecture-design.md)。下表是当前处置状态；“已设计”表示方案已定但仍需在对应开发阶段通过真机验收。

## 首次评审问题记录（历史）

以下章节保留首次评审时的现状、风险和原建议。当前执行方案以文首处置状态表及已更新的需求、架构文档为准。

### 1. 蜂窝语音能力尚未完成端到端验证

**现状**

需求采用 `ATD<number>;`、`ATA` 和 `AT+CHUP` 实现语音通话，但模组支持语音不代表目标地区、运营商、SIM 套餐和模组固件组合一定可用。若通话依赖 2G 回落，还会受到当地网络退网情况影响。

**风险**

- 完成电话 UI 后才发现目标 SIM 无法呼入或呼出。
- VoLTE 未开通、IMS 未注册或模组固件不支持目标运营商配置。
- 数据上传正常但语音不可用，导致核心产品目标失败。

**建议**

在开发桌面和电话 UI 前，使用目标 SIM 做最小硬件验证：

1. 查询网络注册、信号和 IMS/VoLTE 状态。
2. 完成真实呼出、呼入、接听、主动挂断和对方挂断。
3. 验证通话期间 GNSS 查询和数据连接的表现。
4. 记录运营商、SIM 套餐、模组固件版本和必要配置。

该验证应作为项目继续投入的 P0 门槛。

### 2. A7670 UART 缺少唯一所有者和 AT 调度器

**现状**

电话、GNSS、HTTP/MQTT 上传都使用 GPIO17/18 上的同一条 A7670 UART。当前架构把它们描述成多个服务，但没有规定谁独占串口、如何匹配响应、如何分发异步 URC，以及高优先级通话事件如何抢占上传。

**风险**

- 多个任务交错写入 AT 命令，破坏命令边界。
- 普通响应与 `RING`、`NO CARRIER` 等 URC 混在一起后被错误消费。
- 大照片上传占用串口时无法及时处理来电或挂断。
- 超时后的迟到响应被误认为下一条命令的结果。

**建议**

新增唯一 `Modem Manager`，并由它独占 UART 驱动和接收解析器：

- 所有业务通过命令队列提交结构化请求，禁止直接调用 UART。
- 同一时间只运行一个 AT 事务，每个事务包含命令、期望响应、超时和取消策略。
- 接收端按行解析，将命令响应和异步 URC 分流。
- 来电、挂断、网络掉线等 URC 使用高优先级事件通道。
- 明确优先级：通话控制高于 GNSS 查询，GNSS 查询高于普通上传。
- 明确上传被通话打断后的取消、恢复或重试规则。
- 对超时事务设置代次编号或清理窗口，避免迟到响应污染后续事务。

架构图中的 `Modem / Call Service` 建议拆成 `Modem Manager` 与使用它的 `Call Service`、`Location Service`、`Upload Scheduler`。

### 3. 当前接线无法实现软件亮度调节

**现状**

需求把 `LCD_BL` 固定接到 3.3V，背光常亮；架构中的 NVS 设置却包含屏幕亮度。

**风险**

设置页提供无法生效的选项，或者后期为了亮度控制被迫修改已焊接硬件。

**建议**

二选一并写入正式需求：

- 第一版删除屏幕亮度设置，明确背光固定常亮。
- 修改硬件接线，通过可 PWM 控制的 GPIO 或背光驱动电路控制 `LCD_BL`。

此外，`LCD_RST` 和 `TP_RST` 也固定接到 3.3V。应验证 MCU 软件重启后，ST7796S 能否通过软件命令可靠复位，以及 FT6336U 异常后是否能在没有硬件复位脚的情况下恢复。

### 4. 启动绑带脚需要整机冷启动验证

**现状**

GPIO3、GPIO45、GPIO46 是 ESP32-S3 启动绑带脚。当前方案中：

- GPIO3 用作触摸 I2C SCL，并被上拉到 3.3V。
- GPIO45 连接 A7670 DTR。
- GPIO46 连接摄像头 PCLK。

需求目前只明确提醒 GPIO0 不能误接。

**风险**

外设在上电或复位采样阶段改变绑带电平，可能影响冷启动、ROM 下载或启动配置。板载 GPIO45/46 连接通常由开发板设计处理，但新增 GPIO3 外接上拉仍需要在最终接线状态下验证。

**建议**

在所有外设连接后测试：

1. 断电冷启动至少 50 次。
2. RESET 热重启至少 50 次。
3. USB 下载模式进入和退出。
4. 4G 模组、摄像头和屏幕同时上电时启动。
5. 不同 CAM 开关和模组工作状态下启动。

测试通过前，不应把当前 GPIO 分配标记为最终定版。

### 5. 远程位置、照片和控制指令缺少安全模型

**现状**

云端服务会保存位置、通话状态和照片，圆屏还可以下发“立即上报位置”或“立即拍照”指令。当前方案仅描述数据流，没有身份认证和指令安全要求。

**风险**

- 未授权用户读取位置和照片。
- 攻击者伪造或重放拍照指令。
- 设备密钥泄漏后无法轮换。
- 服务端日志或缓存长期保留敏感数据。

**建议**

云端阶段至少定义：

- 设备唯一身份和首次配网/绑定流程。
- HTTPS 或 MQTTS，以及服务端证书校验策略。
- 每个请求的认证、时间戳、随机数和防重放机制。
- 控制指令的唯一 ID、有效期、执行结果和幂等规则。
- 家属账户授权、照片访问控制和数据保留周期。
- 凭据安全存储、吊销和轮换方案。

在安全模型完成前，可以实现本地桌面和设备功能，但不应开放公网远程拍照接口。

## 重要设计缺口

### 6. 电话状态机不能直接覆盖真实模组行为

当前状态图只有 `Idle`、`Incoming`、`Dialing` 和 `InCall`，还需要覆盖：

- 无网络、SIM 不可用和注册失败。
- 忙线、拒接、无人接听和拨号超时。
- 对方接听、对方挂断和网络中断。
- AT 命令失败、重复 URC 和乱序事件。
- 应用 UI 销毁后仍然持续的通话。
- 系统重启或 Modem Manager 重启后的状态重新同步。

实现前应根据 A7670 实际 URC 和查询命令，建立“模组事件 → `Call Service` 状态转换 → UI 事件”的映射表。

### 7. 照片上传耗时和抢占策略不明确

以 UART 115200、8N1 估算，300KB 数据仅串口传输的理论时间约为：

$$
t = \frac{300 \times 1024 \times 10}{115200} \approx 26.7\text{s}
$$

该数值还未包含 AT 协议、网络建立和服务器响应时间。“几百 KB”的照片可能长期占用 Modem Manager。

建议：

- 为 JPEG 设置明确的尺寸和质量上限，第一版建议从 100KB 以内开始实测。
- 验证 A7670 与 ESP32-S3 是否能稳定运行在更高 UART 波特率。
- 定义连接、发送和总上传超时。
- 来电时允许取消或暂停照片上传。
- 上传失败采用有上限的退避重试，不无限占用内存或 TF 文件句柄。

### 8. 峰值内存预算尚未建立

目前只量化了四张 `160×240 RGB565` 快照约 300KiB，但峰值场景还可能同时包含：

- LVGL 单缓冲或双缓冲。
- 最多两个后台缓存页面。
- OV5640 一个或多个帧缓冲。
- JPEG 解码输出和缩放临时缓冲。
- TF 卡 I/O 缓冲。
- HTTP/MQTT 发送缓冲。
- FreeRTOS 任务栈和事件负载。

建议在实现计划中建立静态预算表，并用真机记录 PSRAM/SRAM 最低剩余量、最大连续可分配块和各任务栈高水位。在基准完成前，可以先将后台页面缓存限制为一个，再根据数据提高上限。

### 9. 最近任务快照来源和同步时机未定义

由于 LCD MISO 未连接，不能依赖屏幕显存读回。设计必须明确快照来自 LVGL 对象树或渲染缓冲。

建议第一版采用以下路径：

1. APP 进入后台前，由 `UI Task` 对 APP 根对象生成 LVGL 快照。
2. UI Task 只完成必须在 LVGL 上下文内执行的捕获操作。
3. 缩放和格式转换交给 Worker。
4. 结果携带 APP 会话编号；会话已关闭或编号不匹配时释放结果。
5. 捕获或分配失败时立即退化为图标卡片。

还需要验证 LVGL 9 所选版本的 Snapshot API、所需临时内存和 PSRAM 图像作为 `lv_image` 源的兼容性。

### 10. GNSS 与位置上报缺少异常和新鲜度语义

建议增加以下状态和规则：

- `Disabled`、`Starting`、`NoFix`、`Fixed`、`Stale` 和 `Error`。
- 坐标必须携带定位时间、接收时间和精度/卫星信息。
- 失锁后允许显示最后位置，但必须标记其年龄，不能当成实时位置上传。
- 定义模组重启、GNSS 启动失败和连续无定位时的退避策略。
- 上传事件使用位置样本 ID，服务端按 ID 或时间去重。
- 明确“固定周期上传最后位置”和“只有新定位才上传”中的一种语义。

### 11. 全屏 20–30 FPS 目标依赖未确定的 SPI 参数

320×480 RGB565 一帧为 307,200 字节。忽略命令和总线开销时：

- 40MHz SPI 的全屏理论上限约 16.3 FPS。
- 80MHz SPI 的全屏理论上限约 32.6 FPS。

因此 20–30 FPS 不能作为与配置无关的验收指标。应先确定 ST7796S 模块在当前线材、供电和 DMA 配置下的稳定 SPI 频率，并区分：

- 局部脏区刷新目标。
- 桌面分页等全屏动画目标。
- 触摸输入到首个视觉反馈的延迟目标。

如果只能稳定运行在 40MHz，应降低全屏动画帧率或减少动画区域。

### 12. Worker 并发上限和资源安全线尚未定义

“按需 Worker”不能等同于每个请求都创建新任务。建议规定：

- 摄像头、JPEG 解码、TF 读取和上传分别使用固定 Worker 或有界任务池。
- 每种工作队列都有固定长度和满队列行为。
- 相机采集与大图解码不能无限并发。
- 内存安全线触发后拒绝新重任务，并先回收临时缓冲和后台页面。
- 所有大块缓冲声明所有者、释放任务和取消时的释放路径。

## 文档一致性问题

### 13. 开发阶段与验收阶段定义冲突

`需求.md` 中阶段一仅包含点亮屏幕和跑通 LVGL；架构文档中的“第一阶段验收标准”却覆盖桌面、电话、拍照、AT、NVS 和异常注入。

建议重新划分：

1. 硬件冒烟阶段：屏幕、触摸、启动稳定性和基础 Modem 验证。
2. 桌面内核阶段：分页、APP 生命周期、任务管理器、快照和内存回收。
3. 电话集成阶段：Modem Manager、呼入呼出、通话覆盖层和异常状态。
4. 相机与相册阶段：预览、拍照、TF 存储和解码。
5. 定位与云端阶段：GNSS、上传、安全和圆屏联动。
6. 整机稳定性阶段：并发压力、两小时运行、断网和内存故障注入。

架构文档当前的验收项可改名为“桌面与整机集成验收”，不应继续称为第一阶段。

### 14. 38PIN 与 40PIN 排针描述不一致

接口图和开发板资料显示板上为 38PIN，即两侧各 19 个引脚；需求写的是“配件里的 40PIN 排针”。

应确认实物后修改为以下其中一种准确描述：

- 配件为 2×20 的 40PIN 排针，需要裁成两条 1×19 后焊接。
- 配件实际是两条 1×19 排针，文档统一称为 38PIN 排针。

同时应补充排针焊接方向和 1 号脚识别方式，避免整体错位一针。

### 15. 软件版本和组件来源没有锁定

目前只规定 ESP-IDF v5.x 和 LVGL 9.x。正式实现前应锁定：

- ESP-IDF 精确版本或 commit。
- LVGL 精确版本。
- `esp_lvgl_port`、`esp32-camera` 和 ST7796S 驱动组件的版本与来源。
- 项目依赖锁文件和已验证的 `sdkconfig.defaults`。

否则 LVGL API、组件默认配置或驱动行为变化会使文档和代码难以复现。

## 已确认合理的设计

以下方向建议保留：

- LVGL 仅由一个 UI Task 调用，后台任务不直接操作 LVGL 对象。
- APP 控制器与长期系统服务分离。
- 通话和定位不依赖 APP UI 会话存活。
- 使用会话编号丢弃页面销毁后的迟到事件。
- 最近任务采用有限数量的低分辨率静态快照，并提供图标卡降级。
- APP 页面缓存有明确上限，内存不足时可以销毁并重建。
- 系统覆盖层独立于 APP 页面栈。
- NVS 只保存低频、小体积配置，不保存照片和运行时快照。
- 不追求该 SPI 屏上的 60 FPS，也不在 UI 回调中执行阻塞操作。

需要强调：FreeRTOS 任务共享地址空间，当前方案提供的是组件、调度、状态和生命周期隔离，不是手机操作系统的进程级内存隔离。

## 推荐执行顺序

### P0：硬件和产品可行性门槛

1. 使用目标运营商和 SIM 实测语音呼入、呼出及 VoLTE/网络注册。
2. 验证最终接线下的冷启动、RESET 和下载模式。
3. 确认背光和复位脚接线是否需要调整。
4. 确认 38PIN/40PIN 排针实物和焊接说明。

### P1：基础架构定版

1. 引入唯一 `Modem Manager`，定义 AT 事务、URC 路由和优先级。
2. 补齐电话与 GNSS 状态机。
3. 锁定 ESP-IDF、LVGL 和关键组件版本。
4. 定义 Worker 并发上限和跨任务资源所有权。

### P2：性能与资源基准

1. 实测稳定 SPI 时钟、全屏刷新率和触摸延迟。
2. 确定 LVGL 缓冲配置和快照实现。
3. 建立摄像头、JPEG、快照、页面缓存和上传的峰值内存预算。
4. 实测不同 JPEG 大小在阶段 0 已验证的数据链路和 HTTPS 下的上传耗时，并验证来电抢占。

### P3：联网功能上线前门槛

1. 定义设备身份、TLS、鉴权、防重放和凭据轮换。
2. 定义位置新鲜度、上传重试和服务端去重。
3. 定义远程拍照指令的授权、有效期、幂等和审计规则。

## 阶段门槛

当前设计已经足以编写分阶段实施计划，但实施必须从硬件冒烟阶段开始。进入桌面内核和完整功能开发前，阶段 0 必须确认：

- 临时中国移动卡的真实呼入、呼出、接听、挂断和通话数据并发预验证通过。
- GPIO15/16 上的触摸与 OV5640 共享总线验证通过。
- 最终 GPIO 接线通过 50 次冷启动、50 次 RESET 和下载模式测试。
- A7670 USB descriptors 已确认；USB Host CDC-ACM/PPP 候选路径能稳定建立、断开和重连并与 UART AT/URC 并行，或重新评审后的替代链路通过同等验证。
- 40MHz SPI 基线、软件复位、一个后台页面缓存和图标任务卡降级可用。

最终运营商 SIM、套餐和主要使用地区的语音/数据复测属于上线门槛，不阻塞阶段 0 使用临时移动卡验证基础链路。公网远程拍照只有在 HTTPS、凭据保护、命令过期与防重放全部验收后才能启用。
